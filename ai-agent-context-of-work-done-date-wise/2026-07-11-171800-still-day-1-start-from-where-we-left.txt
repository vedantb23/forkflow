  📎 SETUP: Redis via Docker (concept first — this is new for you)

  What Redis is (plain language): an in-memory key–value store. Think of it as a
  giant, extremely fast dictionary that lives in RAM instead of on disk.
  Because it's in RAM, reads/writes are ~microseconds. We'll use it for 4 jobs
  in this project:
  1. Cache — store restaurant/menu data so we don't hit Postgres on every page
  load (Day 3).
  2. Locks — the "only one order can grab the last item" mechanism (Day 4).
  3. Queues — BullMQ runs on top of Redis to process orders in the background
  (Day 5).
  4. Counters — kitchen capacity slots, leaderboards (Day 4+).

  What Docker is (plain language): instead of installing Redis onto Windows
  manually (fiddly), Docker runs Redis inside a lightweight isolated "container"
  — a mini pre-configured Linux box. Our docker-compose.yml is the recipe that
  says "run a Redis 7 container on port 6379." One command starts it.

  Before the command — a prerequisite check. You need Docker Desktop installed
  and running.
  - Do you already have Docker Desktop? If yes, start it (open the app, wait for
  the whale icon to say "running").
  - If you don't have it: download from
  https://www.docker.com/products/docker-desktop/, install, launch it, and let
  it finish starting.

  Once Docker Desktop is running, tell me — then I'll give you the exact docker 
  compose up -d redis command (with a full explanation of every flag) and we'll
  connect the backend to it.

  What broke

  tsconfig.json(6,25): error TS5108: Option 'moduleResolution=node10' has been

  Why it happened

  When we installed deps last session, the ^ version ranges pulled TypeScript 7
  (typescript@7.0.2) — that's the brand-new native TypeScript compiler. TS 7
  removed the old moduleResolution: "node" setting (it was internally called
  node10). Our tsconfig.json still uses the old value, so tsc refuses to run.

  Note: this never showed up when you ran npm run dev, because tsx (what dev
  uses) is a looser/faster runner that ignored it. Only the strict tsc
  typecheck/build catches it. Good that we caught it now on Day 1 and not on Day
  7's build.

  The fix

  Switch module and moduleResolution to the modern nodenext pairing. Bonus:
  nodenext actually respects packages' exports maps (the old node didn't), so
  imports like dotenv/config resolve more correctly. Since our package.json has
  no "type": "module", files are still treated as CommonJS — so node 
  dist/server.js keeps working exactly as before.

  Your database password is BGzJ7@V3YRjPLLs — it contains an @ character. In a
  connection URL, @ is the special character that separates the password from
