  🧠 Concept: what Socket.io is and why we need it (you're new to this)

  Right now your app is request/response only: the browser asks (GET 
  /orders/123), the server answers, done. The connection closes. If the order
  status changes 2 minutes later, the browser has no idea — it would have to
  keep re-asking ("polling"), which is wasteful and laggy.

  Socket.io keeps a connection open between browser and server (a WebSocket).
  Either side can send a message at any time. So when your worker flips an order
  to PREPARING, the server can push that down the open pipe and the customer's
  screen updates instantly, no refresh. That's "live order tracking."

  Three ideas we'll use:
  - Rooms — a socket can "join" a named room like order:123. When we emit to
  that room, only sockets in it get the message. So customer A watching order
  123 doesn't see order 456's updates.
  - Handshake auth — when a browser connects, we verify its JWT before letting
  it in (same token as your REST API). No token = no socket.
  - Redis adapter — the piece that makes your two processes cooperate (the thing
  you just chose). More on that when we build it.

● File 5/5 — realtime/socket.ts (the io server + Redis adapter)

  Concept — the Redis adapter (this is the key architectural piece): Socket.io
  normally keeps its list of "who's in which room" in the memory of one process.
  But your app has two processes — the API (where browsers connect) and the
  worker (where order status changes). The worker needs to reach a browser it
  has no direct connection to.

  The Redis adapter solves this: it moves Socket.io's room-messaging through
  Redis Pub/Sub. When anything publishes an "emit to order:123" through Redis,
  the API process (which holds that browser's connection) picks it up and
  delivers it. This is also what would let you run multiple API servers behind a
  load balancer. It needs two Redis connections (pub + sub) because a
  connection in "subscribe mode" can't run normal commands.
