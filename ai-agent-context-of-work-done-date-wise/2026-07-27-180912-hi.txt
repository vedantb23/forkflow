  4. BACKEND API REFERENCE (so each screen binds to real data)

  Base URL /api. Auth = JWT in httpOnly cookie (also Bearer). Realtime via
  Socket.io (order:status_updated, delivery:location_updated). Roles: CUSTOMER,
  RESTAURANT_OWNER, DELIVERY, ADMIN.

  Auth /api/auth — POST /register {name,email,password,phone?,role?} (role
  defaults CUSTOMER) · POST /login {email,password} · GET /me (drives role
  routing/nav) · POST /logout

  Users /api/users — GET /me, PATCH /me (profile) · GET / ADMIN only →
  /admin/users

  Restaurants /api/restaurants — GET / public list → home · GET /mine
  (OWNER/ADMIN) → owner switcher · GET /:id public detail → restaurant page ·
  POST /, PATCH /:id, DELETE /:id (OWNER/ADMIN, multipart image)

  Menu /api/menu — GET /:restaurantId public → restaurant page · GET 
  /:restaurantId/owner (OWNER/ADMIN, incl. unavailable) → menu mgmt · POST 
  /:restaurantId, PATCH /items/:itemId, DELETE /items/:itemId (OWNER/ADMIN,
  multipart image)

  Cart /api/cart (customer, single-restaurant) — GET / → cart · POST /items 
  {menu_item_id,quantity} · PATCH /items/:menuItemId {quantity} · DELETE 
  /items/:menuItemId · DELETE / (empty)

  Orders /api/orders — POST / (send Idempotency-Key header)
  {restaurant_id,items[]} → checkout · GET / my orders · GET 
  /restaurant/:restaurantId (OWNER/ADMIN) → KDS · GET /:orderId → tracking/owner
  detail · PATCH /:orderId/status {status} (OWNER/ADMIN). Statuses: PENDING → 
  CONFIRMED → PREPARING → OUT_FOR_DELIVERY → DELIVERED | CANCELLED

  Delivery /api/delivery — GET /available (DELIVERY) → job feed · POST /assign 
  {order_id,partner_id} (OWNER/ADMIN) · GET /:orderId assignment · PATCH 
  /:orderId/status {status} (DELIVERY) · POST /:orderId/claim (DELIVERY, "Accept
  Trip") · PATCH /:orderId/location {lat,lng} (DELIVERY, also live over socket
  → map). Statuses: UNASSIGNED → ASSIGNED → PICKED_UP → DELIVERED

  Admin tooling: a Bull queue dashboard lives at /admin/queues — link it from
  the admin "Queues" nav.
